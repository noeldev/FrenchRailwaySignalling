# SignalBot

Applies the fixes of the validator rule table of a country (`validator/rules.json` for France) to the railway signals already in OpenStreetMap, as a documented automated edit. It makes the same corrections as the JOSM validator fixes and the MapRoulette challenge generated by MapRouletteGen (it uses the same `Signalling.Rules` and `Signalling.Schema` libraries), without a click per signal.

It is written to follow the [Automated Edits code of conduct](https://wiki.openstreetmap.org/wiki/Automated_Edits_code_of_conduct). The table below is the map between the policy and the code; nothing here replaces the first two requirements, which are not code: **document the edit (in English or in the language of the country) and announce it to the community before any real run**.

| Policy | In the tool |
|---|---|
| Work on the current data, never overwrite a recent edit | Overpass only lists the candidates. Each batch is read again from the OSM API just before it is decided and uploaded, each node with the version it was read at. On a conflict the server refuses the whole upload; the batch is read and decided again, never forced (`EditRunner`). |
| A stated list of changes, discussed; any extension discussed again | `rules` writes the exact list of the corrections for the page documenting the edit. Every report gives the hash of the rule table the run used. |
| Only trivial, certain corrections | Fixes that guess (`suggest`) or need a manual complement (a rule `note`) are left to a human, as are conflicts, blocked rules and undocumented tags (`FixPlanner`, `policy` settings). |
| Respect the mappers | Only the signals of the mappers who opted in can be fixed (`--opted-in`): a node is fixed when the mapper of its last version, the one the map shows, is on the list, checked again on the fresh data before the upload. A node edited in the last 24 hours is left alone (`quietPeriodHours`). Nodes can be opted out (`optOut`). |
| Start small, get feedback | The sandbox server is the default; `plan` is a dry run; `apply` is bounded by `--limit` (200 by default) and can be limited to an area (`--area`) or to the nodes last edited by one mapper (`--mapper`), for example your own. |
| Changesets grouped in small regions, good comments | Changesets split by squares of 1 degree (`maxChangesetSpanDegrees`, under the bounding box limit the server sets for new accounts), at most 500 nodes each, comment in the language of the country naming the country or the filter area. A node is edited once, with all its fixes. |
| Identify the edits | Dedicated account, checked before the first write; `bot=yes`, `mechanical=yes`, `created_by` and `description` (the page documenting the edit) on every changeset; settings without them are refused. |
| Be able to revert | Every run writes a journal with the tags before and after; `revert` restores them on the nodes nobody edited since. |
| Document what was done | Every run writes `report.md`: areas, changesets with links, tag changes, rules applied and counts. |

## Getting started

Start the program without arguments (in Visual Studio: F5 on the project). It asks for the server, then offers only the steps that can be taken now, in their order, the next one by default:

| Server | Steps |
|---|---|
| `prod`, the real map | `plan`; `login` until logged in; `apply` once logged in; `revert` after an `apply`; `logout` once logged in. |
| `dev`, the sandbox | `login` until logged in; `seed` once logged in; `plan` and `apply` once test nodes exist; `revert` after an `apply`; `logout` once logged in. |

After each step, the program lists the files it wrote and what to check in them. Nothing is written to a server without a confirmation where the name of the server must be typed.

The session asks in this order, and every menu can be left without Ctrl+C:

1. **Server** - `dev`, `prod`, or `exit`.
2. **Signals** (real map only; a sandbox has the test nodes) - `all` (every signal of the country), `area` (regions or departments; the codes are checked at once, an empty answer goes back) or `mapper` (the mappers who opted in); `back` returns to the server.
3. **Mappers**, for the `mapper` choice - the list of the opted-in mappers with their uid, and a menu shown again after each change: `opt-in` adds mappers, one display name per line until an empty line (each name is checked on the server, which gives its uid); `opt-out` removes mappers, one per line, by their number in the list or by display name; `continue` goes on with the list; `back` returns to the signals.
4. **Step** - the table above, plus `signals` (choose other signals), `server` (choose another server) and `exit`. The server and the signals chosen are shown above the steps and kept from one step to the next, so `plan` and `apply` cover the same signals.

Before a step runs, a short summary tells what it is about to do, followed by `Do you want to proceed? (y/n) [n]`. A "no" does nothing and returns to the steps.

```
[apply] on server 'prod'
  Signals: last edited by the 43 opted-in mappers
  Action:  upload at most 200 fixes as 'signalbot'
Do you want to proceed? (y/n) [n]:
```

The access token of a server does not expire: once logged in, `login` is no longer offered and nothing is asked in the browser. `logout` revokes the token on the server and forgets the account and its client ID on this computer; `login` then asks for them again, which is the way to change the account or the client ID.

The opted-in mappers are kept per country in the user profile (see Settings), never in the repository: the identifiers of mappers are not committed.

## Commands

| Command | What it does | Writes to the server |
|---|---|---|
| `plan` | Dry run: the report of what `apply` would do. | no |
| `apply` | Uploads the fixes. | yes |
| `revert` | Restores the tags the last `apply` run replaced (or the run of a given journal), on the nodes nobody edited since. | yes |
| `seed` | Sandbox only: creates test nodes copied from real signals to fix (50 by default), so that `apply` and `revert` can be tried there. The sandbox is a separate database, without the signals of the real map. | yes, sandbox only |
| `login` | Registers the OAuth 2 application if needed and authorizes the bot account, guided; saves the account, client ID and token. | no |
| `logout` | Revokes the access token on the server and forgets the account, client ID and token on this computer. The application stays registered on the account. | no |
| `rules` | Writes the list of the corrections (command line). | no |

The same commands run from the command line, for scripts: `SignalBot plan --server prod --area BRE`. Run `SignalBot --help` for the options. The source is the whole country by default; `--area` (regions or departments, `--area BRE`, `--area 14,75`) and `--mapper` (`--mapper "Noël Danjou"`) or `--opted-in` (the mappers who opted in) filter it and combine; `--input` reads an Overpass answer instead (for example one saved by an earlier run) and `--nodes` a list of node ids. On the sandbox, `plan` and `apply` work on the test nodes of the last `seed`.

A run can be stopped with Ctrl+C: the current changeset is completed and closed first. There is no checkpoint file to manage: running the same command again resumes the work, because every decision is taken on fresh data and a fixed signal is no longer a candidate.

## Countries

Everything that depends on a country is in its profile, `countries/<code>.json` (ISO 3166-1 code, `FR.json` for France): the area of the country, the wiki pages of the scheme, the key and value prefixes, the rule table, the scope, the kinds of filter areas, the changeset comments in the language of the country and the opted-out nodes. Another country adds its own profile (and its rule table); with several profiles, the program asks for the country, and the command line takes `--country <code>`. The output and the test nodes are kept per country.

The filter areas of a profile are listed in `areaKinds`: a pattern to recognize the code, the Overpass area statement to select it, its format and examples. For France:

| Area | Code | Examples |
|---|---|---|
| Region | ISO 3166-2 code without the `FR-` prefix (tag `ISO3166-2`) | `BRE`, `NOR`, `IDF`, `20R` |
| Department | INSEE code (tag `ref:INSEE`) | `14`, `75`, `2A`, `69D`, `974` |

A department is selected by its INSEE code rather than by ISO 3166-2, which differs for some of them (Paris is `FR-75C`). The Rhone is `69D` and the Metropole de Lyon `69M`. A filter area is named in the changesets after its `name` in OpenStreetMap.

## When Overpass fails

Overpass is a shared server, often loaded: timeouts are expected. It only lists the candidate signals, so a failure can never write anything wrong, but a partial list would silently leave signals out. The rules:

- The query carries its time limit (`overpass.timeoutSeconds`, 600 s), and the program waits one minute longer than that for the answer, so it never gives up on a query the server is still running.
- A transient failure is tried again (`overpass.retries`, 3 times), after a wait that doubles each time (`overpass.retryDelaySeconds`, 30 s, then 60 s, 120 s), or the wait the server asks for: no answer in time, `429` (rate limit), `5xx` (load), a connection cut off, truncated JSON, or an answer the server could not complete (it then sends what it found with a `remark`: such a partial answer is always refused).
- With several addresses in `overpass.endpoints`, each new try goes to the next one.
- A query the server refuses (`400`) is not tried again: its error message is shown.
- When every try failed, the command stops before anything is written, with the reason. Run it again later; nothing has to be undone.
- An answer is saved (`overpass-<area>.json`) only when it is complete. The program shows the time of the OSM data it was computed on, and warns when Overpass is hours behind.

Overpass is queried with an HTTP client of its own, which never carries the access token of the bot account.

## Output

Everything is written under `bot/runs/<country>/` (setting `output`, ignored by git). Each run writes a folder named after its start time, command and server (`offline` for an offline plan):

- `report.md` - the report to publish: areas, changesets (with links to the changeset and to OSMCha), tag changes (`+` added, `-` removed, `~` changed), rules applied, nodes left untouched and why, last mappers of the edited nodes;
- `changes-NNN.osc` - the osmChange document of each batch, as uploaded (or as it would be, in a dry run). JOSM opens these files, which is a convenient way to review a dry run;
- `journal.jsonl` - [JSON Lines](https://jsonlines.org/), one JSON object per line (an editor that expects a single JSON document, like Visual Studio, reports "only one top-level item is allowed": the file is right, and need not be reformatted): the run, each batch with the tags of every node before and after (written before the upload), the result of the upload, each skipped node with its reason. This is the input of `revert`: keep the journals of the real runs;
- `overpass-<area>.json` - the data received from Overpass, which `plan --offline --input <file>` reads again.

Besides: `corrections.md` and `corrections.wiki` (written by `rules`), and `seeded-nodes-<server>.txt`, the ids of the test nodes of the last `seed`. The folders of dry runs can be deleted at any time.

## Settings

`appsettings.json` holds what does not depend on a country: servers, Overpass endpoints, time limit, retries and query, changeset tags, policy and limits. The values of the operator are written by the program itself in the user profile, never in the repository, and there is nothing to edit by hand:

- `%APPDATA%\SignalBot\settings.json` - the account (its display name, not the e-mail address) and the client ID of each server, written by `login`;
- `%APPDATA%\SignalBot\opted-in-<country>.json` - the mappers who opted in (uid and display name), written by the interactive session;
- `%APPDATA%\SignalBot\tokens.json` - the access tokens, written by `login`.

The first one has the layout of `appsettings.json` and is read over it, for example `{ "servers": { "prod": { "account": "...", "clientId": "..." } } }`.

## Accounts

The same account logs in to the sandbox (`dev`, https://master.apis.dev.openstreetmap.org) and to the production server (`prod`, https://www.openstreetmap.org), but each server has its own OAuth 2 application, hence its own client ID: run `login` on each. On `prod`, the edit is made with a dedicated account; on its profile, say what it is and link to the page documenting the edit.

`login` does the rest: it asks whether the OAuth 2 application is already registered on the account; if not, it opens the registration page and shows the values to type (the application is public: no client secret is used), otherwise it opens the list of the applications of the account, where the name of the application leads to its client ID; it then asks for the client ID, opens the authorization page, asks for the code shown, then checks and records the name of the account.

A new account is limited by the server in the number of edits per hour and in the size of the area of a changeset (hence the batches by squares). When the edit rate limit is reached the run stops cleanly; run the same command again later.

## When the rule table changes

The page documenting the edit lists the corrections it makes. After a change of the rule table, run `rules` and update that list with `corrections.wiki`.

The hash of the rule table is computed with LF line ends, so it is the same whatever the line ends of the checkout.

## Tests

`SignalBot.Tests` runs the whole pipeline against an in-memory OSM API (`FakeOsmServer`) that refuses version conflicts like the real one: fresh data, conflicts, limits, opt-in and opt-out, dry run, journal and revert; and the parts around it: command line, settings, opted-in mappers, changeset batches, test nodes, tag changes, the Overpass client against an interpreter that fails in every way listed above (`FakeOverpass`), and the menus of the interactive session with a scripted operator.
