# SignalBot

Applies the fixes of the validator rule table of a country (`validator/rules.json` for France) to the railway signals already in OpenStreetMap, as a documented automated edit. It makes the same corrections as the JOSM validator fixes and the MapRoulette challenge generated by MapRouletteGen (it uses the same `Signalling.Rules` and `Signalling.Schema` libraries), without a click per signal.

It is written to follow the [Automated Edits code of conduct](https://wiki.openstreetmap.org/wiki/Automated_Edits_code_of_conduct). The table below is the map between the policy and the code; nothing here replaces the first two requirements, which are not code: **document the edit on the wiki and discuss it with the community before any real run**.

| Policy | In the tool |
|---|---|
| Work on the current data, never overwrite a recent edit | Overpass only lists the candidates. Each batch is read again from the OSM API just before it is decided and uploaded, each node with the version it was read at. On a conflict the server refuses the whole upload; the batch is read and decided again, never forced (`EditRunner`). |
| A stated list of changes, discussed; any extension discussed again | `rules` writes the exact list of the corrections for the wiki page. Outside the sandbox, `apply` only runs with the rule table whose hash was recorded after the discussion (`approvedRulesSha256`). |
| Only trivial, certain corrections | Fixes that guess (`suggest`) or need a manual complement (a rule `note`) are left to a human, as are conflicts, blocked rules and undocumented tags (`FixPlanner`, `policy` settings). |
| Respect the mappers | A node edited in the last 24 hours is left alone (`quietPeriodHours`). Mappers and nodes can be opted out (`optOut`): a node an opted-out mapper ever edited is skipped (its history is read), not only the nodes they edited last. |
| Start small, get feedback | The sandbox server is the default; `plan` is a dry run; `apply` is bounded by `--limit` (200 by default) and can be limited to an area (`--area`) or to the nodes last edited by one mapper (`--mapper`). |
| Changesets grouped in small regions, good comments | Changesets split by squares of 1 degree (`maxChangesetSpanDegrees`, under the bounding box limit the server sets for new accounts), at most 500 nodes each, comment in the language of the country naming the country or the filter area. A node is edited once, with all its fixes. |
| Identify the edits | Dedicated account, checked before the first write; `bot=yes`, `mechanical=yes`, `created_by` and `description` (the wiki page) on every changeset; settings without them are refused. |
| Be able to revert | Every run writes a journal with the tags before and after; `revert` restores them on the nodes nobody edited since. |
| Document what was done | Every run writes `report.md`: areas, changesets with links, tag changes, rules applied and counts. |

## Getting started

Start the program without arguments (in Visual Studio: F5 on the project). It asks for the server, then offers only the steps that can be taken now, in their order, the next one by default:

| Server | Steps |
|---|---|
| `prod`, the real map | `plan`; `approve` until the rule table is approved; `login` until logged in; `apply` once both are done; `revert` after an `apply`. |
| `dev`, the sandbox | `login` until logged in; `seed` once logged in; `plan` and `apply` once test nodes exist; `revert` after an `apply`. |

After each step, the program lists the files it wrote and what to check in them. Nothing is written to a server without a confirmation where the name of the server must be typed.

`plan`, `apply` and `seed` ask which signals to take: every signal of the country, those of an area (region or department), or those last edited by one mapper, for example your own.

## Commands

| Command | What it does | Writes to the server |
|---|---|---|
| `plan` | Dry run: the report of what `apply` would do. | no |
| `apply` | Uploads the fixes. | yes |
| `revert` | Restores the tags the last `apply` run replaced (or the run of a given journal), on the nodes nobody edited since. | yes |
| `seed` | Sandbox only: creates test nodes copied from real signals to fix (50 by default), so that `apply` and `revert` can be tried there. The sandbox is a separate database, without the signals of the real map. | yes, sandbox only |
| `login` | Registers the OAuth 2 application if needed and authorizes the bot account, guided; saves the account, client ID and token. | no |
| `approve` | Writes the list of the corrections, then records the current rule table as the one `apply` may use on the server; `apply` refuses any other. | no |
| `rules` | Writes the list of the corrections only (command line). | no |

The same commands run from the command line, for scripts: `SignalBot plan --server prod --area BRE`. Run `SignalBot --help` for the options. The source is the whole country by default; `--area` (regions or departments, `--area BRE`, `--area 14,75`) and `--mapper` (`--mapper "Noël Danjou"`) filter it and combine; `--input` reads an Overpass answer instead (for example one saved by an earlier run) and `--nodes` a list of node ids. On the sandbox, `plan` and `apply` work on the test nodes of the last `seed`.

A run can be stopped with Ctrl+C: the current changeset is completed and closed first. There is no checkpoint file to manage: running the same command again resumes the work, because every decision is taken on fresh data and a fixed signal is no longer a candidate.

## Countries

Everything that depends on a country is in its profile, `countries/<code>.json` (ISO 3166-1 code, `FR.json` for France): the area of the country, the wiki pages of the scheme, the key and value prefixes, the rule table, the scope, the kinds of filter areas, the changeset comments in the language of the country and the opt-out list. Another country adds its own profile (and its rule table); with several profiles, the program asks for the country, and the command line takes `--country <code>`. The output, the test nodes and the approved rule tables are kept per country.

The filter areas of a profile are listed in `areaKinds`: a pattern to recognize the code, the Overpass area statement to select it, its format and examples. For France:

| Area | Code | Examples |
|---|---|---|
| Region | ISO 3166-2 code without the `FR-` prefix (tag `ISO3166-2`) | `BRE`, `NOR`, `IDF`, `20R` |
| Department | INSEE code (tag `ref:INSEE`) | `14`, `75`, `2A`, `69D`, `974` |

A department is selected by its INSEE code rather than by ISO 3166-2, which differs for some of them (Paris is `FR-75C`). The Rhone is `69D` and the Metropole de Lyon `69M`. A filter area is named in the changesets after its `name` in OpenStreetMap.

## Output

Everything is written under `bot/runs/<country>/` (setting `output`, ignored by git). Each run writes a folder named after its start time, command and server (`offline` for an offline plan):

- `report.md` - the report to publish: areas, changesets (with links to the changeset and to OSMCha), tag changes (`+` added, `-` removed, `~` changed), rules applied, nodes left untouched and why, last mappers of the edited nodes;
- `changes-NNN.osc` - the osmChange document of each batch, as uploaded (or as it would be, in a dry run). JOSM opens these files, which is a convenient way to review a dry run;
- `journal.jsonl` - one JSON object per line: the run, each batch with the tags of every node before and after (written before the upload), the result of the upload, each skipped node with its reason. This is the input of `revert`: keep the journals of the real runs;
- `overpass-<area>.json` - the data received from Overpass, which `plan --offline --input <file>` reads again.

Besides: `corrections.md` and `corrections.wiki` (written by `approve` and `rules`), and `seeded-nodes-<server>.txt`, the ids of the test nodes of the last `seed`. The folders of dry runs can be deleted at any time.

## Settings

`appsettings.json` holds what does not depend on a country: servers, Overpass endpoint and query, changeset tags, policy and limits. The values of the operator are written by the program itself in the user profile, never in the repository, and there is nothing to edit by hand:

- `%APPDATA%\SignalBot\settings.json` - the account (its display name, not the e-mail address) and the client ID of each server, written by `login`;
- `%APPDATA%\SignalBot\<country>.json` - the approved rule table of each server, written by `approve`;
- `%APPDATA%\SignalBot\tokens.json` - the access tokens, written by `login`.

The first two have the layout of `appsettings.json` and are read over it, for example `{ "servers": { "prod": { "account": "...", "clientId": "..." } } }`.

## Accounts

The sandbox (`dev`, https://master.apis.dev.openstreetmap.org) and the production server (`prod`, https://www.openstreetmap.org) do not share accounts: create the account on each. On `prod`, the edit is made with a dedicated account: its name is the one of the wiki page `Automated edits/<name>`; on its profile, say what it is and link to that page.

`login` does the rest: it asks whether the OAuth 2 application is already registered on the account; if not, it opens the registration page and shows the values to type (the application is public: no client secret is used), otherwise it opens the list of the applications of the account, where the name of the application leads to its client ID; it then asks for the client ID, opens the authorization page, asks for the code shown, then checks and records the name of the account.

A new account is limited by the server in the number of edits per hour and in the size of the area of a changeset (hence the batches by squares). When the edit rate limit is reached the run stops cleanly; run the same command again later.

## When the rule table changes

The edit is discussed for a stated list of corrections. After any change of the rule table, `apply` on `prod` refuses to run until it is approved again:

1. Run `approve` (or `rules`) and replace the content of the wiki page `Automated edits/<account>/Corrections` with `corrections.wiki`; announce the change in the discussion.
2. Once accepted, confirm `approve` on `prod`.

The hash of the rule table is computed with LF line ends, so it is the same whatever the line ends of the checkout.

## Tests

`SignalBot.Tests` runs the whole pipeline against an in-memory OSM API (`FakeOsmServer`) that refuses version conflicts like the real one: fresh data, conflicts, limits, opt-out, dry run, journal and revert; and the parts around it: command line, settings, changeset batches, test nodes, tag changes.
